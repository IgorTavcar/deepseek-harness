seq 0006 Service Definition · Provider · Consumer

A seam is the whole capability, never one role.

Cordis already answers “who provides versus who needs a service.” Package boundaries answer a slower question: the contract, the implementation, and the model-facing consumer change at different rates. Bundle them and swapping bash for a sandbox churns the schema the model sees.

Three roles

  1. Service Definition — the Cordis Service that owns ctx.<key> and the vocabulary types. An abstract class such as ShellExecutor, or a concrete registry such as WebRuntime. Never a TypeScript interface.
  2. Service Provider — a plugin that supplies or registers an implementation. dsh-bash-local, dsh-bash-sandbox, dsh-fs-e2b.
  3. Consumer — what the model and other plugins program against. dsh-tool-bash injects ctx.shell and never imports provider types.

Roles normally occupy separate packages when they evolve independently. They stay folded when they are one concern: dsh-llm owns Definition and Consumer because the Consumer is the loop, not a swappable schema. Do not split preemptively.

The word seam is reserved for the trio. Name a constituent by its role, class, service, contract, or extension point. Confusing this with Cordis's permission service @cordisjs/plugin-capability is the trap the Agent Note exists to name.

One execution world

Filesystem and subprocess together define a path namespace and a process world. Bash, the PTY backend, and the LSP host consume those two interfaces. Point both at E2B and terminals plus language servers move with them. No provider forks. The host keeps the loop, the log, credentials, and the LLM. The remote world is ephemeral files and processes, not “the whole harness in a box.”

Sandbox is a third, narrower seam: consumers hand over the exact argv they are about to spawn; a backend wraps it under per-call policy. ctx.sandboxPolicy is the one home for default mode and workspace root so bash and fs cannot confine to different roots.

Resolve, then run

The shell template is the standing order at every package boundary. A caller submits a partial ShellExecRequest. The owning implementation resolves it to a complete ShellExecSpec before execution. Defaulting is that step, never a hidden ?? inside run(). Deployment-varying choices are validated Config fields. Protocol constants and security invariants stay fixed. Misconfiguration fails loud.
