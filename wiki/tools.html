The registry owns visibility, execution, and how the model is allowed to call.

A tool is a typed definition, a guarded pipeline, a canonical JSON value that never hits the log, and a pure card the UI can replay. PTC mode is not a second product. It is a presentation mode of the same registry.

The pipeline, in order

1Assistant message contains a tool-call block. Loop appends tool/call with the raw argument string.
2tools/pre-execute waterfall: hooks, permission, sandbox. allow / deny / ask.
3ctx.approval services ask. Absent or unanswerable degrades to deny.
4Monotonic tools.guard(). A reason denies. Later listeners cannot un-deny.
5tools/execute around the body: timeout, retry, metrics. Wrappers may replace only signal; the registry re-fuses the caller signal.
6Tool body. Filesystem mutations also pass fs/write-intent / fs/edit-intent.
7tools/post-execute: accept, replace content or value, block, attach context.
8Definition-owned finalizeContent: last synchronous content-only invariant, including on failures.
9Observe-only tools/result, then durable tool/result. Additional contexts FIFO after the recorded result.

Arguments are snapshotted and frozen at the start of execute. Invalid arguments use the same result path without reaching policy. Cancellation before the body is ABORTED_BEFORE_DISPATCH. After invocation, cancellation can replace only a successful outcome with ABORTED; a more specific denial, timeout, or tool failure wins.

Pre-execute cannot rewrite arguments. Logged and rendered args would desync from what ran. That rewrite is a proposed note, not a missing feature someone should sneak in.

Canonical value versus model-facing content

Every definition must declare output: { schema, render, presentationMeta? }. The body returns only the canonical JSON value. The registry snapshots, validates, freezes, then renders content. Post-execute may replace content or value, never both. Value replacement revalidates and rerenders. Content replacement is not a confidentiality boundary: block or replace the value when programmatic consumers must not receive it.

Canonical values are execution-local. They never enter the session log. Replay reconstructs presentation, not the DTO. That split is why PTC can return typed ToolOutputMap values inside a worker without bloating history.

Tools own their cards

presentCall and presentResult return a closed union: generic, terminal, diff, and result-only search, read, web. UIs do not special-case tool names. Presenters are pure functions of arguments plus the durable result, so live streaming and log replay share one path. A tool's render intent is part of its design, decided up front. Returning undefined selects generic fallback.

PTC mode

Cloudflare named the observation Code Mode: models are better at writing code than at emitting tool-call JSON, and intermediate tool results do not all belong in the next prompt. The registry's name for the presentation is PTC. The closed union is native (default), ptc, or both. An agent may presentAs(mode) to shadow that for itself. The shipped ptc preset sets mode: ptc and disables the general workflow tool so the model does not get a second orchestration surface beside run_code; Ralph and the worker-thread engine stay mounted.

Under ptc or both:

  • The registry contributes reserved transport run_code { code, description }. The name cannot be registered, restricted, shadowed, or removed.
  • Lazy section tools:sdk emits a byte-stable SDK for the loaded ctx.codeRuntime.language — TypeScript ToolArgsMap / ToolOutputMap, or Python TypedDicts. Lexicographic tool order, prefix-cache friendly. Under ptc the prompt also carries tools:ptc-only earlier in first-party order.
  • Under ptc only, a model-direct call naming any other tool is UNKNOWN_TOOL before policy, with a teaching message to call it from inside the program. Nested dispatches that carry a parent token are exempt.
  • Each await tools.name(args) re-enters the complete native pipeline. Failures become ToolCallError(toolName, message). Success returns the canonical JSON value, never rendered Native prose.
  • Only console.log and return re-enter model context. Intermediate values stay in the worker, unbounded by bytes. Sub-calls log historical types tool/code-dispatch-start / tool/code-dispatch for the UI; the live waterfall tools/ptc-dispatch-log may change only that durable copy. deriveMessages() ignores them.
  • Settlement aborts and drains so every sub-result lands inside the open turn. The inner pool reuses exclusive/parallel classification (maxParallelSubCalls, default 10).

There is no persistent REPL. Cross-run state would be invisible to the log. Arguments must be lossless JSON: undefined, BigInt, cycles, sparse arrays, -0, and exotic objects reject that one call.

The runtime knows nothing about tools

ctx.codeRuntime receives a program and named async bindings and reports { value, logs, error? }. Language and isolation are backend descriptors. The shipped provider is a fresh Node worker thread per run: type-stripped TypeScript, empty env, heap/time/output caps, hard termination. The port protocol assumes a hostile peer because the peer runs model code.

Trust is bash-equivalent by design. The harness already ships a local shell that executes arbitrary model-written commands with more ambient authority. PTC does not invent a safer world; it invents a better calling convention.
